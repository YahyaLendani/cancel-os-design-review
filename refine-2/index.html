Design review: refine 2

Hierarchy, row actions, menus and motion, on top of the glass-and-depth slice. On Android, the subscription list has one Import action and no duplicated "More" section, and the account line is moved below the subscriptions. On the website, each subscription row has one primary action and a contextual menu. Both platforms' menus now use the same measurements. The logo's lift-and-return loop is re-timed. The palette, the cut-tile logo, the solid surfaces behind money and the restrained glass on navigation are unchanged.

Every screen uses synthetic test data (account wizard@example.test, services named "Synthetic …") on a local stand-in server, in headless Chrome or the Android emulator. No real person's data appears.

This is a public preview. Anyone with the link can open it. It asks search engines not to index it, but that is a request, not access control.

What changed

  • Android list. The count comes first, then one Import button with its line "Read a CSV or PDF on this phone, then review before anything is saved". The "More" section is removed: it repeated Import and the header menu. Explore services, Reminder settings and Settings now live only in the header's More options menu, so every function is still reachable. "Signed in as …" moved to the end, beside Sign out.
  • Website rows. Up to six equal buttons became three controls:
    • How to cancel (the old "Cancel" link, renamed so it cannot be read as "cancel this edit");
    • Edit, the row's one primary action;
    • More actions for <name>, a menu holding Cheaper plans and Alternatives (when the row is matched to a merchant), Watch or Unwatch, and Remove, last and apart, in the error red.
    The menu follows the WAI-ARIA menu-button keyboard model.
  • Menus, measured the same on both platforms. See the table below. The Android menu is now opaque: at the previous 94% tint the words beneath showed through, and Android here has no blur.
  • Motion. The logo's tilt peaks at 7° (was 9°). The tile answers the corner's landing with one faint push. The cycle lasts 2 s, including 0.4 s of rest (was 1.8 s). It runs only while real work is pending and is static under reduced motion. Menus act first, then fade out over 120 ms, and opening one again mid-fade reverses the fade. Navigation transitions were reviewed and left unchanged. No amount is animated.

Research note: the brief asked for Mobbin. No Mobbin skill or connector was available, so none was used and no Mobbin reference is claimed. The keyboard model comes from the WAI-ARIA Authoring Practices (read), and the menu's surface from Material Components for Android's menu documentation (read). Two patterns are from memory and were not checked against the guidelines: "secondary destinations in the overflow menu" and "destructive item last and apart". No named app was studied.

What was checked

  • Website (1280 px light and dark, 390 px, 200% zoom, reduced motion): 33 of 33 checks, covering the row's controls and their names, the menu's anchoring and flip, 44 px items, keyboard (Enter, Space, Up, Down, Home, End, typeahead, Escape returning focus, Tab moving on), no sideways scroll at 390 px or 200%, and no scale or movement under reduced motion.
  • Android (light and dark at 100%, light at 200%): 31 of 31 checks, covering one Import action, no "More" section, the account line after the subscriptions, and the menu's anchoring and 48 dp items. Explore services, Reminder settings, Settings and Import each opened. The existing Android journey check: 43 of 43.
  • Contrast: 194 of 194 token checks, including the error red on the menu glass over every ground (lowest 4.88:1).

Remove's behaviour is unchanged, and has no confirmation step. It never had one, and none was added. Remove is now the last item in the row's menu. Choosing it submits the same per-row delete form as before, and the item's accessible name names its row ("Remove Synthetic Cloud A").

The check behind this pressed Remove with the page's form submission intercepted, so nothing was sent. It established that Remove submits its own row's delete form, the menu closes at once, and the row stays on the page. It does not establish an end-to-end deletion result: no deletion was performed or observed in this slice.

A first-load Edit failure in one website check, investigated. On a fresh build, the check pressed a row's Edit as soon as the server-rendered row appeared, and no editor opened.

  • Method: the same press was compared at aa20820 and daf2e7b under the same fresh-build conditions, 90 presses each.
  • Cause: every lost press landed in the first moments of hydration, 2–15 ms after React attached its click listener and before the Edit button was hydrated.
  • The race predates this slice: 5 of 90 presses were lost at aa20820, 11 of 90 at daf2e7b. Those rates cannot be told apart with this sample (p = 0.19), so whether refine 2 makes a lost press more likely remains open.
  • No lost interaction: a press after hydration opened the editor every time in both trees, and neither logged a hydration error.
  • Hydration is slightly later: about 13 ms at the median (113 → 126 ms after navigation).

The check now presses Edit until the editor opens, the repository's existing pattern for this. It passed on a fresh and a reused build, with the editor opening on the first press both times, so the retry itself has not yet run in a real check. Evidence: commit 283dfce.
